infrastructure reserve подтверждены владельцем workspace 4 октября 2026 года.
Остальные персональные роли ниже — предложения на основе существующего
CODEOWNERS, ожидающие явного согласия участников. История коммитов не использована

Storefront и admin: CODEOWNERS перечисляет двух участников без разделения ролей.
Предложенный порядок направляет штатную работу владельцам соответствующих UI,
сохраняя @alex-vitup резервным reviewer. До подтверждения этот порядок не считается
согласованным назначением.

Владелец компонента отвечает за реализацию, tests, документацию, совместимость
интерфейсов и исправление дефектов своей области. Резервный reviewer проверяет
изменения при отсутствии основного владельца и PR самого основного владельца.
Резервная роль не означает автоматического получения production-доступа.
Автор отвечает за self-QA и evidence; reviewer — за критерии Issue, регрессии и
результаты необходимых проверок.

## Инфраструктурные зоны во всех репозиториях

| Зона | Основной владелец | Границы |
| --- | --- | --- |
| CI/CD | @dumpe2fs | Workflows приложений и общие build/publish/deploy workflows в vstore-infra |
| Docker | @dumpe2fs | Dockerfile, .dockerignore, Compose и startup/entrypoint mechanics |
| Nginx | @dumpe2fs | Edge/TLS в vstore-infra/config/nginx; app proxy в vstore-front/nginx и vstore-admin/nginx |
| Production-доступы | @dumpe2fs | VM/SSH, Azure, repository Secrets и deployment credentials; доступ предоставляется отдельным решением |
| Инфраструктурная безопасность | @dumpe2fs | Сеть, hardening контейнеров, права, secrets и security checks инфраструктуры |

Изменения business logic и схемы БД остаются за backend owner; изменения UI и
использования API — за соответствующим UI owner. Изменение Nginx/API proxy требует
участия владельца приложения и владельца инфраструктуры. Наличие пути в CODEOWNERS
не переносит ответственность за business logic в инфраструктуру.

**Исключение infrastructure:** по решению владельца workspace постоянный резерв
не назначается, в том числе для production-доступов. При отсутствии @dumpe2fs
инфраструктурная работа и операции с доступами могут ожидать его возвращения.
Это известная граница цели снижения зависимости от одного участника, а не
подтверждение взаимозаменяемости infrastructure owners.

Для PR @dumpe2fs, затрагивающего инфраструктуру, до merge отдельно определяется
независимый компетентный reviewer. При его отсутствии PR остаётся на review;
self-approval и AI-review не заменяют человеческий review. Исключение по резерву
пересматривается в Issue #1 при расширении команды, блокировке review или
необходимости передачи эксплуатации. Production credentials в Issue/PR не пишутся.

## Как выбрать reviewer

1. Найти компонент и инфраструктурные зоны, затронутые PR.
2. Вручную запросить review основного владельца; если он автор PR или недоступен —
   резервного reviewer. До подтверждения роли уточнить согласие кандидата в Issue #1.
3. Автор и независимый reviewer должны быть разными участниками. Для PR резервного
   reviewer основной владелец может выполнить review. Если оба недоступны, отметить
   blocker в Issue с необходимым reviewer и следующим действием; согласовать замену.
4. Для CI, Docker, Nginx, deployment и доступа включить владельца инфраструктуры.
   Для его собственного PR применяется порядок независимого review из исключения.
5. Для нескольких компонентов перечислить владельцев в Issue/PR, согласовать
   контракт API, migration и порядок rollout до реализации зависимых изменений.
   Каждый владелец проверяет свою часть, автор координирует связанные PR и evidence.

Штатные backend/storefront/admin PR после подтверждения матрицы не требуют
отдельного участия Team Lead. Конфликты ответственности, существенный риск и
отсутствие доступного reviewer передаются Team Lead, а не скрываются как approval.

## GitHub Free и подтверждение назначений

Проект использует GitHub Free для приватных репозиториев. CODEOWNERS служит
справочником путей и участников. Автоматическое назначение owners, обязательные
approvals и техническая блокировка merge через CODEOWNERS/branch protection не
заявляются. Review запрашивается вручную и проверяется участниками команды.

Существующие справочники: [backend](https://github.com/vstore-ex/vstore/blob/main/.github/CODEOWNERS),
[storefront](https://github.com/vstore-ex/vstore-front/blob/main/.github/CODEOWNERS),
[admin](https://github.com/vstore-ex/vstore-admin/blob/main/.github/CODEOWNERS),
[infrastructure](https://github.com/vstore-ex/vstore-infra/blob/main/.github/CODEOWNERS).

Для принятия роли участник фиксирует в Issue #1 или связанном PR свой GitHub login,
компонент, основную/резервную роль и согласие на перечисленные обязанности.
Координатор переносит ссылку на подтверждение в таблицу. Командное решение может
быть зафиксировано протоколом с согласиями участников; merge документа сам по себе
не подтверждает согласие всех перечисленных людей.

TL-01 подтверждается только после публикации ссылок из четырёх README, получения
согласий на роли и проверки выбора независимого reviewer по матрице. Infrastructure
принимается с указанным исключением. Issue #1 остаётся открытым, пока эти evidence
не получены. Полный процесс веток/review/merge оформляется следующим шагом TL-02.


## PR template для GitHub UI, CLI и AI — TL-03

Задача и evidence автоподстановки: [Issue #5](https://github.com/vstore-ex/Docs/issues/5).
Шаблон находится в `.github/pull_request_template.md` каждого component repo.
После публикации в default branch GitHub UI должен подставлять его в новый PR;
проверка этого поведения по каждому репозиторию фиксируется в Issue #5.

Автор заполняет все семь разделов: проблема/ожидаемое поведение, Issue/критерии,
реализация, проверки/self-QA, migrations/compatibility/deployment, UI evidence,
ограничения/rollback. Неприменимый раздел содержит «Не применимо». Описание остаётся
кратким и не пересказывает diff; подсказки удаляются после заполнения.

Для CLI выполнить из корня нужного component repo:

```bash
cp .github/pull_request_template.md /private/tmp/vstore-pr-body.md
# Заполнить файл, удалить подсказки и проверить фактические результаты.
gh pr create --base main --title 'chore: краткая цель изменения' \
  --body-file /private/tmp/vstore-pr-body.md
```

Путь `/private/tmp` в примере относится к macOS workspace; в другом окружении
использовать доступный временный каталог. Заголовок выбрать по типу изменения
(feat/fix/chore/ci). Для каждого PR подготовить отдельное описание и передать
актуальный заполненный файл; автоматический PR не должен публиковать пустой template.
AI заполняет те же поля и явно перечисляет отсутствующие проверки, доказательства и
человеческие решения. Если local feature branch ещё не содержит template, использовать
его из default branch соответствующего repo после merge либо текущий файл TL-03 PR.

Reviewer проверяет наличие и правдивость сведений, соответствие Issue и текущему
HEAD. Template не является технической блокировкой merge. `Closes`/`Fixes` допустимы
только при выполнении всех критериев завершения; иначе использовать `Refs` и оставить
задачу открытой. Успешный CI не заменяет self-QA, review и проверку deployment.
