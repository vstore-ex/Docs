Владелец компонента отвечает за реализацию, tests, документацию, совместимость
интерфейсов и исправление дефектов своей области. Резервный reviewer проверяет
изменения при отсутствии основного владельца и PR самого основного владельца.
Резервная роль не означает автоматического получения production-доступа.
Автор отвечает за self-QA и evidence; reviewer — за критерии Issue, регрессии и
результаты необходимых проверок.

| Зона | Основной владелец | Границы |

Изменения business logic и схемы БД остаются за backend owner; изменения UI и
использования API — за соответствующим UI owner. Изменение Nginx/API proxy требует
участия владельца приложения и владельца инфраструктуры. Наличие пути в CODEOWNERS
не переносит ответственность за business logic в инфраструктуру.

**Исключение infrastructure:** по решению владельца workspace постоянный резерв
не назначается, в том числе для production-доступов. При отсутствии @dumpe2fs
инфраструктурная работа и операции с доступами могут ожидать его возвращения.
Это известная граница цели снижения зависимости от одного участника, а не
подтверждение взаимозаменяемости infrastructure owners.

Для PR @dumpe2fs, затрагивающего инфраструктуру, до merge отдельно определяется
независимый компетентный reviewer. При его отсутствии PR остаётся на review;
self-approval и AI-review не заменяют человеческий review. Исключение по резерву
пересматривается в Issue #1 при расширении команды, блокировке review или
необходимости передачи эксплуатации. Production credentials в Issue/PR не пишутся.

## Как выбрать reviewer

1. Найти компонент и инфраструктурные зоны, затронутые PR.
2. Вручную запросить review основного владельца; если он автор PR или недоступен —
   резервного reviewer. До подтверждения роли уточнить согласие кандидата в Issue #1.
3. Автор и независимый reviewer должны быть разными участниками. Для PR резервного
   reviewer основной владелец может выполнить review. Если оба недоступны, отметить
   blocker в Issue с необходимым reviewer и следующим действием; согласовать замену.
4. Для CI, Docker, Nginx, deployment и доступа включить владельца инфраструктуры.
   Для его собственного PR применяется порядок независимого review из исключения.
5. Для нескольких компонентов перечислить владельцев в Issue/PR, согласовать
   контракт API, migration и порядок rollout до реализации зависимых изменений.
   Каждый владелец проверяет свою часть, автор координирует связанные PR и evidence.

Штатные backend/storefront/admin PR после подтверждения матрицы не требуют
отдельного участия Team Lead. Конфликты ответственности, существенный риск и
отсутствие доступного reviewer передаются Team Lead, а не скрываются как approval.

## GitHub Free и подтверждение назначений

Проект использует GitHub Free для приватных репозиториев. CODEOWNERS служит
справочником путей и участников. Автоматическое назначение owners, обязательные
approvals и техническая блокировка merge через CODEOWNERS/branch protection не
заявляются. Review запрашивается вручную и проверяется участниками команды.

Существующие справочники: [backend](https://github.com/vstore-ex/vstore/blob/main/.github/CODEOWNERS),
[storefront](https://github.com/vstore-ex/vstore-front/blob/main/.github/CODEOWNERS),
[admin](https://github.com/vstore-ex/vstore-admin/blob/main/.github/CODEOWNERS),
[infrastructure](https://github.com/vstore-ex/vstore-infra/blob/main/.github/CODEOWNERS).

Для принятия роли участник фиксирует в Issue #1 или связанном PR свой GitHub login,
компонент, основную/резервную роль и согласие на перечисленные обязанности.
Координатор переносит ссылку на подтверждение в таблицу. Командное решение может
быть зафиксировано протоколом с согласиями участников; merge документа сам по себе
не подтверждает согласие всех перечисленных людей.

TL-01 подтверждается только после публикации ссылок из четырёх README, получения
согласий на роли и проверки выбора независимого reviewer по матрице. Infrastructure
принимается с указанным исключением. Issue #1 остаётся открытым, пока эти evidence
не получены. Правила веток/review/merge приведены ниже в разделе TL-02.

## Единый процесс изменений — TL-02

Задача и evidence применения: [Issue #3](https://github.com/vstore-ex/Docs/issues/3).
Область: четыре компонента VStore и этот репозиторий Docs. Статус: **предложено к
утверждению**. Стратегия Squash and merge и применение процесса подтверждаются
review и протоколом обычного PR в Issue #3; наличие текста не означает согласования.

### От Issue до review

1. Создать или выбрать существующий Issue с проблемой, ожидаемым поведением,
   компонентом, владельцем, приоритетом, границами и проверяемыми критериями.
   Указать зависимости; findings A01–A16 продолжать в существующих Issues.
2. Создать feat/*, fix/* или chore/* от актуальной default branch. Для каждого
   репозитория использовать свою ветку и связать PR, если изменение межкомпонентное.
   Перед staging/commit проверить `git branch --show-current`; работа в main
   запрещена обычным процессом.
3. Выполнить изменение и self-QA: основной сценарий, затронутые ошибки и соседнее
   поведение. Внести необходимые tests, migrations и документацию. Сохранить команды,
   результаты и ссылки на CI; невыполненные проверки перечислить с причиной.
4. Открыть PR со ссылкой на Issue, выполненными критериями, описанием результата,
   проверками, migrations/deployment impact, ограничениями и rollback, если применимо.
   Для видимых UI-изменений приложить screenshots/video, если они помогают review.
   CLI/AI-автор заполняет те же сведения, что автор в GitHub UI.
5. Вручную выбрать и запросить независимого reviewer по таблице выше; отметить
   участников и их область review в PR. Если роль ещё не подтверждена, получить
   согласие на review конкретного PR. Для CI, Docker, Nginx и deployment включить
   infrastructure owner; для его собственных PR отдельно выбрать компетентного
   reviewer. Отсутствие постоянного infrastructure reserve не отменяет независимость.

В GitHub UI review запрашивается через PR → Reviewers. Через CLI:
`gh pr edit <PR> --repo vstore-ex/<repository> --add-reviewer <login>`.
Автор проверяет, что запрос принят GitHub; отсутствующий доступ или ошибка запроса
фиксируются как blocker, а не как назначенный review. AI запрашивает review другого
участника только при явном поручении человека; иначе reviewer назначается человеком.

### Что проверяет reviewer

- Реализация выполняет критерии Issue; существенные ограничения явно перечислены.
- Self-QA содержит результаты, покрывает основной сценарий, ошибки и регрессии.
- Все необходимые проверки завершились успешно для текущего HEAD PR. Failed,
  cancelled, pending и недоступный CI не означают success. Skipped допустим только
  для неприменимого job; пропущенная необходимая проверка требует согласованного
  исключения с причиной, владельцем и условием пересмотра.
- Учитываются migrations, совместимость API, порядок deployment и возможность
  rollback. CI-green не означает подтверждённый production deployment.
- Существенные замечания исправлены; принятый остаточный риск имеет обоснование
  и ответственное решение в PR/Issue. Reviewer подтверждает исправления.
- PR имеет независимый человеческий approval. Автор не подтверждает собственное
  изменение; AI-review дополняет человеческий review.

После новых существенных коммитов автор повторяет затронутые проверки и запрашивает
повторный review. Approvals старого diff не считаются подтверждением нового поведения.
Перед merge ответственный участник проверяет актуальный HEAD, проверки и review.

### Merge и завершение

Предлагаемая единая стратегия — **Squash and merge** с Conventional Commit заголовком
(`feat:`, `fix:`, `chore:`, `ci:`) и ссылкой на Issue. Утверждение стратегии записывается
в Issue #3; документ сам по себе не изменяет разрешённые GitHub merge methods.

Merge выполняет участник с необходимым доступом после независимого approval и
проверок. Затем удаляется завершённая feature-ветка, если она не нужна для другой
работы; связанные незавершённые PR не должны потерять базовую ветку. Main не удаляется.

Issue автоматически закрывается через `Closes`/`Fixes` только когда merge выполняет
все критерии завершения. Иначе используется `Refs`, сохраняются невыполненные пункты
и следующее действие. Для релизной задачи требуются deployment и smoke; выключенная
VM оставляет задачу ожидающей deployment либо ведётся отдельная связанная release
задача. Неудачный deployment не меняет статус на готовый к production.

### Аварийное исключение

Обычным процессом запрещены прямой push и force push в main, а также удаление main.
Недоступный reviewer, красный CI или нехватка квоты сами по себе не разрешают обход.
При инциденте сначала рассматривается исправление через ускоренный PR или штатный
rollback по существующему runbook.

Если это невозможно, **до действия** в Issue инцидента фиксируются:

1. Симптомы и влияние, причина срочности и почему обычный PR/rollback недостаточен.
2. Точный репозиторий, commit/версия, операция и границы предлагаемого исключения.
3. Исполнитель, принимающий решение участник с необходимыми полномочиями и
   независимый reviewer; если reviewer недоступен — явное принятие этого риска.
4. План проверки, целевой rollback и влияние на схему/данные/доступы.
5. Явное решение уполномоченного человека, разрешающее конкретное исключение.

При недоступном GitHub использовать доступный командный канал и затем перенести
протокол в Issue. Если согласованный канал и принимающий решение участник недоступны,
это blocker; документ не предоставляет автоматического аварийного разрешения.
Production restore, удаление данных, расширение доступов и новые расходы требуют
отдельного решения. AI выполняет исключение только по явному разрешению человека.

После действия записать фактические команды без secrets, итоговый commit/digest,
результаты health/smoke, пропущенные проверки и восстановление. Создать связанную
follow-up задачу с владельцем и сроком последующего независимого review, выполнить
пропущенные проверки и согласовать устранение причины обхода. Инцидент не считается
закрытым до проверки восстановления; follow-up не теряется после его закрытия.

### Права и границы GitHub

Admin выдаётся только тем, кому необходимо управлять repository settings, доступами
и Secrets; остальным достаточно соответствующих обязанностям прав. Write позволяет
участвовать в разработке, но не разрешает обходить этот процесс. Изменение permissions
выполняется по отдельному поручению, этот документ не выдаёт новых прав.

На GitHub Free/private команда вручную контролирует approval, состояние CI и merge.
Технический запрет прямого push или merge при красном CI здесь не заявляется.
Согласование правил и прохождение одного обычного PR с назначенным reviewer,
self-QA, CI, review и merge фиксируются ссылками в Issue #3. До этого TL-02 остаётся
частично выполненным; TL-01 отдельно ожидает подтверждения персональных ролей.
