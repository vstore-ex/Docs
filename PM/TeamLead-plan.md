# План развития инженерных процессов VStore

Дата редакции: 4 октября 2026 года.
Область действия: vstore, vstore-front, vstore-admin и vstore-infra.
Цель: снизить зависимость разработки и эксплуатации от одного участника команды, обеспечить воспроизводимую проверку изменений и передать ответственность владельцам компонентов.

## 1. Принципы выполнения плана

Каждая задача оформляется отдельным GitHub Issue с владельцем, приоритетом, областью изменений и проверяемыми критериями приёмки. Изменения выполняются в отдельной ветке и передаются на review через Pull Request.

Наличие файла, workflow или инструкции не означает завершения задачи. Завершение подтверждается проверкой заявленного поведения и ссылкой на результат: PR, CI run, протокол тестирования или эксплуатационный отчёт.

Статусы задач: «Не начато», «В работе», «Частично выполнено», «Подтверждено», «Требует проверки», «Заблокировано». Отметка выполнения допускается только при наличии доказательства. Состояние задач в GitHub является основным; этот документ определяет требования и порядок работы.

Приоритеты:
- P0 — организационная или техническая проблема, блокирующая безопасную работу проекта.
- P1 — необходимое условие работоспособности MVP и предсказуемого релиза.
- P2 — снижение эксплуатационных рисков и зависимости от отдельных участников.
- P3 — улучшения после выполнения обязательных требований.

Приоритеты A01–A16 в ранее выполненном DevOps-аудите сохраняют собственную шкалу. Их обозначения не следует автоматически переводить в шкалу этого документа.

## 2. Ограничения платформы и бюджета

Используется GitHub Free для организации с приватными репозиториями. Переход на платный тариф и публикация исходного кода не входят в план.

Доступны PR и Issue templates, Issues/Projects, обычный review, repository Secrets, Dependabot alerts и обновления зависимостей. GitHub Actions используются в пределах квоты организации: 2 000 минут в месяц на стандартных runners и 500 MB хранения artifacts, общего с обычными GitHub Packages. Использование larger runners и платного перерасхода не планируется.

Branch protection, Rulesets и встроенный CODEOWNERS для приватных репозиториев на выбранном тарифе не обеспечивают предусмотренный процесс. Обязательные approvals, запрет прямого push и запрет merge при красном CI фиксируются в правилах команды. GitHub технически не блокирует их нарушение. Существующие CODEOWNERS-файлы могут служить справочником ответственности.

Вместо платных GitHub Code Security и Secret Protection используются открытые инструменты с результатами в CI logs или artifacts. Загрузка результатов в GitHub Code scanning не входит в план. Organization Secrets/variables и environment Secrets для приватных репозиториев заменяются repository Secrets/variables.

Хранение и передача container images в GHCR сейчас бесплатны по отдельной политике GitHub. Эта политика не распространяется на все виды Packages и подлежит повторной проверке при изменении условий сервиса.

Azure VM, Blob Storage, внешнее хранение backups и дополнительные preview-окружения имеют отдельную стоимость. Существующие ресурсы используются в пределах утверждённого бюджета; новые ресурсы требуют оценки расходов.

## 3. P0 — ответственность за компоненты и порядок review

### TL-01. Утвердить владельцев компонентов и резервных reviewers

Результат: опубликованный справочник ответственности в CONTRIBUTING.md или связанном документе.

Содержание:
- Для backend, storefront, admin и infrastructure назначить основного владельца и резервного reviewer.
- Указать зоны ответственности: реализация, тесты, документация, review и исправление дефектов.
- Отдельно определить владельцев CI/CD, Nginx, Docker, production-доступов и инфраструктурной безопасности.
- Для изменений нескольких компонентов определить участвующих владельцев и порядок согласования интерфейсов.
- Назначения подтвердить участниками команды. История коммитов не является достаточным основанием для назначения владельца.

Критерии приёмки:
- Для каждого репозитория указан основной и резервный reviewer.
- Автор PR может определить reviewer без обращения к Team Lead.
- Для PR основного владельца предусмотрен независимый reviewer.
- Отсутствие Team Lead не блокирует обычные изменения backend, storefront и admin.

Ответственные: Team Lead и владельцы компонентов; AI подготавливает справочник и проверяет покрытие зон.

### TL-02. Установить единый процесс внесения изменений

Результат: согласованные правила работы с ветками, review и merge.

Содержание:
- Изменения выполняются в feat/*, fix/* или chore/* и передаются через PR.
- Автор вручную запрашивает review владельца компонента.
- Перед merge reviewer проверяет выполнение критериев Issue, CI, self-QA и закрытие существенных замечаний.
- Изменения CI, Docker, Nginx и deployment проходят review владельца инфраструктуры.
- Используется согласованная стратегия merge; рекомендуемый вариант — Squash and merge.
- После merge удаляется завершённая feature-ветка, если она не используется для другой работы.
- Прямой push, force push и удаление main запрещены правилами команды. Аварийное исключение фиксируется с причиной, участниками и последующей проверкой.
- Права Admin предоставляются только участникам, которым требуется управление настройками; права Write не трактуются как разрешение обходить процесс.

Критерии приёмки:
- Правила опубликованы и доступны из README репозиториев.
- Один обычный PR проходит полный процесс с назначенным reviewer.
- Аварийный порядок не требует скрытых знаний одного участника.
- Документация явно указывает отсутствие технического запрета merge на GitHub Free.

### TL-03. Добавить шаблоны Pull Request

Результат: .github/pull_request_template.md в default branch каждого репозитория.

Обязательные поля:
- проблема и ожидаемое поведение после изменения;
- ссылка на Issue и выполненные критерии приёмки;
- краткое описание реализации;
- выполненные проверки с командами или ссылками на CI;
- миграции, несовместимые изменения и влияние на deployment;
- screenshots или video для видимых UI-изменений;
- ограничения, известные дефекты и способ отката, если применимо.

Критерии приёмки:
- При создании PR через GitHub интерфейс подставляется шаблон.
- Неприменимые поля допускают явное указание «Не применимо».
- Шаблон не требует повторного описания всего diff.
- Для CLI и AI-созданных PR предусмотрено заполнение тех же полей.
- Заполнение контролируется reviewer; шаблон не является технической блокировкой.

## 4. P0 — воспроизводимая проверка изменений

### CI-01. Зафиксировать матрицу проверок для каждого репозитория

Результат: документ с командами, зависимостями окружения и условиями успешного CI.

Backend:
- lint и существующий test suite;
- создание схемы через Alembic и проверка отсутствия schema drift;
- интеграционные проверки API с PostgreSQL и Redis;
- сборка Docker image и проверка старта приложения;
- проверка существующего endpoint /health;
- проверка зависимостей через pip-audit по согласованной политике.

Storefront и admin:
- воспроизводимая установка через npm ci;
- lint и production build;
- тесты критических UI-сценариев;
- Docker build и проверка запуска Nginx;
- проверка /healthz и доступности API через proxy;
- проверка зависимостей через npm audit.

Infrastructure:
- Compose validation с безопасными тестовыми параметрами;
- проверка синтаксиса Nginx и proxy smoke;
- существующие infrastructure tests;
- проверка конфигурации Docker и сканирование образов, включая edge proxy.

Критерии приёмки:
- Для каждой проверки указано, запускается ли она на PR, main или вручную.
- Существенная ошибка завершает соответствующий job с failed status.
- Проверки не подменяются успешным warning без согласованного исключения.
- Исключения содержат причину, владельца и условие пересмотра.
- Publish/deploy jobs зависят от успешных проверок.
- Reviewer проверяет CI перед merge; автоматическая блокировка кнопки merge не заявляется.

### CI-02. Ограничить расход GitHub Actions

Результат: конфигурация CI, укладывающаяся в доступную квоту.

Содержание:
- Использовать стандартные runners.
- Отменять устаревшие PR runs, если это не прерывает production deployment.
- Установить разумные timeout и срок хранения artifacts.
- Сохранять только необходимые диагностические отчёты без секретов и пользовательских данных.
- Регулярно проверять Billing usage и настройки остановки платного перерасхода.

Критерии приёмки:
- Зафиксированы ответственный за квоту и порядок действий при её исчерпании.
- Задокументирован локальный запуск проверок при недоступности Actions.
- Недостаток квоты не трактуется как успешное выполнение CI.

## 5. P1 — качество и критерии завершения

### QA-01. Ввести обязательную самопроверку автором изменения

Результат: reviewer получает изменение с подтверждённой базовой работоспособностью.

Критерии приёмки:
- Автор проверяет основной сценарий, затронутые ошибки и соседнее поведение.
- В PR указаны конкретные результаты, а не только «Проверено».
- UI-изменения сопровождаются изображениями или записью поведения, если это помогает review.
- Не выполненные проверки перечислены вместе с причиной.
- Reviewer оценивает решение и регрессии; первый запуск изменения не переносится на reviewer.

### QA-02. Определить и автоматизировать критические сценарии

Результат: согласованный набор примерно из 10–20 сценариев с распределением по уровням тестирования.

Начальный перечень: регистрация, login/logout, права доступа, каталог, поиск, карточка игры, корзина/заказ и другие операции MVP, admin login и CRUD, состояния отсутствия данных и ошибок API.

Backend-проверки включают API ↔ PostgreSQL, auth, migrations, Redis и отрицательные сценарии. Blob Storage проверяется изолированно; обращение к внешнему сервису допускается при наличии отдельного тестового ресурса и бюджета.

Критерии приёмки:
- Для каждого сценария определены ожидаемый результат и уровень проверки: unit, integration, UI/E2E или ручная regression.
- Tests изолируют PostgreSQL и Redis state между запусками.
- Migrations проверяются на схеме, созданной Alembic, а не только ORM metadata.
- Основные сценарии выполняются воспроизводимо без production-данных.

### QA-03. Согласовать Definition of Ready и Definition of Done

Definition of Ready:
- определены проблема, цель, компонент и границы изменения;
- указаны проверяемые критерии приёмки;
- назначен владелец;
- описаны зависимости и существенные неизвестные;
- продуктовые решения, необходимые для начала, приняты.

Definition of Done:
- критерии приёмки выполнены;
- необходимые tests и migrations включены в PR;
- CI и self-QA завершены;
- документация обновлена при изменении поведения или эксплуатации;
- независимый review завершён;
- изменение merged;
- для релизной задачи подтверждены deployment и smoke.

Критерии приёмки:
- Оба определения опубликованы и используются в Issues/PR.
- Merge и production readiness различаются: при выключенной VM задача остаётся ожидающей deployment либо содержит отдельную связанную релизную задачу.
- Статус Done не скрывает невыполненные проверки или отложенный deployment.

## 6. P1 — управление задачами

### PM-01. Организовать единый backlog и Kanban

Результат: GitHub Issues и Projects позволяют определить состояние работы без личного уточнения у Team Lead.

Содержание:
- Использовать статусы Backlog → Ready → In Progress → Review → Done.
- Для каждой задачи указать владельца, приоритет, критерии приёмки и зависимости.
- Большие задачи разделять на изменения, которые можно независимо проверить.
- PR связывать с Issue; автоматическое закрытие применять только когда merge удовлетворяет критерию завершения.
- Заблокированные задачи отмечать с причиной, следующим действием и ответственным за снятие блокировки.
- Ограничить активную работу одним-двумя заданиями на разработчика.

Критерии приёмки:
- Текущая работа команды представлена в Projects.
- Ready-задача может быть начата без повторного согласования базовых требований.
- Незавершённые задачи не теряются при появлении новых задач.
- Findings DevOps-аудита используются через существующие Issues, без создания дубликатов.

## 7. P1 — документация и передача знаний

### DOC-01. Подготовить минимальный комплект инженерной документации

Результат: новый участник или резервный владелец может запустить проект, проверить изменение и выполнить штатную диагностику.

Документы:
- ARCHITECTURE.md: компоненты, связи, API/proxy path, PostgreSQL, Redis, Blob Storage, ports, trust boundaries и модель deployment.
- DEVELOPMENT.md: clone, dependencies, безопасная .env setup, запуск, migrations, tests, lint и debugging.
- CONTRIBUTING.md: ownership, Issues, ветки, PR, review, merge, self-QA, DoR/DoD.
- DEPLOYMENT.md: build/publish/deploy, digests, health/smoke, повторный запуск, rollback и ограничения отката схемы.
- TROUBLESHOOTING.md: симптомы, проверки, вероятные причины и действия для unhealthy backend, недоступной БД, ошибок migration/pull/deploy, proxy/API и нехватки диска.
- SECURITY.md: хранение secrets, права доступа, ротация credentials и действия при утечке.

Критерии приёмки:
- Документы ссылаются на существующие команды и конфигурацию.
- Уже существующие README/runbooks переиспользованы, противоречащие инструкции устранены.
- Секреты и production-данные отсутствуют.
- Резервный участник выполняет минимум один сценарий запуска или диагностики по документу.
- Повторяющиеся вопросы используются как основание для уточнения документации.

## 8. P1 — deployment и инфраструктурная безопасность

### OPS-01. Обеспечить сохранение состояния релиза и проверяемый rollback

Результат: следующий deployment использует ожидаемые версии приложений, а rollback имеет известную цель.

Критерии приёмки:
- Успешные и предыдущие image digests сохраняются между SSH-сессиями.
- App и infrastructure deployment читают одно согласованное состояние версий.
- Проверенный artifact совпадает с публикуемым и развёрнутым artifact.
- Deployment выполняется последовательно под общим lock.
- Ошибка deployment видна в CI; недоступная VM не приводит к ложному success.
- Rollback возвращает предыдущие версии images; восстановление БД выполняется по отдельной процедуре.
- Доказательства связаны с существующими задачами A01, A09 и A10.

### OPS-02. Добавить проверку пользовательского пути после deployment

Результат: success означает доступность приложения через внешнюю точку входа.

Критерии приёмки:
- Проверяются storefront, разрешённый маршрут admin, backend /health и критический API endpoint через edge.
- После пересоздания backend proxy продолжает работать при смене IP.
- Redirects и доверенные proxy headers сохраняют корректные HTTPS и client IP.
- Пробы не создают заказы, не изменяют пользовательские данные и не расходуют общие production rate limits без специального сценария.
- Failed smoke завершает deployment ошибкой; определён порядок восстановления.
- Работа связана с A02, A03 и A11.

### SEC-01. Закрепить базовую безопасность GitHub, VM и контейнеров

Результат: минимальные необходимые права, контролируемые secrets и воспроизводимая конфигурация защиты.

Содержание:
- CI credentials хранятся в repository Secrets; Actions имеют минимальные permissions.
- История Git и изменения проверяются на secrets открытым сканером.
- SSH использует ключи; password authentication и root SSH запрещены или оформлены явным обоснованным исключением.
- Проверены host firewall и Azure NSG; снаружи доступны только необходимые ports.
- PostgreSQL и Redis не доступны из Internet.
- Docker socket не предоставляется приложениям без отдельного обоснования.
- App containers используют non-root, ограничения capabilities, restart policy, log rotation и разумные лимиты ресурсов.
- Images и зависимости проверяются, исправляемые vulnerabilities устраняются либо принимаются с документированным исключением.
- Проверены права deployment directory, .env и backups.
- Для Blob Storage подтверждена необходимость публичного доступа к конкретным объектам; доступ к media не закрывается без проверки использования приложением.

Критерии приёмки:
- Зафиксированы результаты проверок, владельцы и незакрытые риски.
- Секреты не присутствуют в Git, Docker build context и диагностических artifacts.
- Порядок security updates и credential rotation документирован.
- Исправления связаны с A03, A05, A13 и A16.

## 9. P1/P2 — наблюдаемость и восстановление

### OBS-01. Ввести минимальный мониторинг и actionable alerts

Результат: обнаруживаются недоступность, ошибки, деградация и исчерпание ресурсов.

Содержание:
- VM: CPU, RAM, swap, disk usage и load.
- Containers: running state, restart count и потребление ресурсов.
- Backend: availability, latency и HTTP 5xx.
- PostgreSQL: availability, connections и storage.
- Alerts: backend unavailable, crash loop, disk threshold и устойчивый высокий error rate.
- Для каждого alert задать длительность условия, адресата и ссылку на runbook.

Критерии приёмки:
- Выбран минимальный набор инструментов, подходящий имеющейся VM.
- Пробный отказ на стенде вызывает уведомление и последующее recovery-событие.
- Короткие безвредные пики не вызывают постоянных уведомлений.
- Доступны резервный получатель и порядок действий при недоступности основного владельца.
- Пиковая нагрузка и запас RAM исследуются в рамках A15; дополнительная инфраструктура согласуется по бюджету.

### LOG-01. Обеспечить диагностику ошибок по логам

Результат: обращение о HTTP 500 можно сопоставить со временем, запросом и причиной ошибки.

Критерии приёмки:
- Backend logs содержат timestamp, level, request/error context и stack trace для необработанных ошибок.
- Контекст не содержит passwords, tokens, secrets и избыточных пользовательских данных.
- Определены доступ к logs, retention и rotation.
- Reviewer или резервный владелец способен найти тестовую ошибку по времени и контексту.
- Централизованное хранение добавляется только при доказанной необходимости.

### REC-01. Определить backup strategy и проверить restore

Результат: подтверждена возможность восстановления после ошибки migration и потери VM.

Содержание:
- Утвердить RPO — допустимую потерю данных по времени, и RTO — допустимое время восстановления.
- Настроить регулярный backup PostgreSQL, retention и хранение вне основной VM.
- Обеспечить ограниченные permissions и защиту backup credentials.
- Проверить restore в отдельную чистую БД с остановкой при SQL errors.
- Проверить schema revision и контрольные данные после восстановления.
- Для Blob Storage определить необходимость versioning, soft delete или backup и стоимость хранения.
- Если Azure Backup уже настроен, проверить его покрытие и процедуру восстановления.

Критерии приёмки:
- Backup не зависит только от очередного deployment.
- Потеря основной VM не уничтожает единственную копию данных.
- Есть протокол успешного restore с измеренным временем.
- Восстановление production-данных требует отдельного решения; автоматическое удаление production БД не предусматривается.
- Работа связана с A04 и A06.

### DATA-01. Определить политику Redis state и изоляции tests

Результат: документированное поведение auth, broker и cache при отказе Redis и ограничении памяти.

Критерии приёмки:
- Классифицированы durable и disposable state.
- Выбраны persistence, memory policy и допустимое поведение при отказе.
- Eviction cache не приводит к потере auth/broker state.
- Integration tests изолируют Redis counters и другие ключи.
- Изменения согласованы backend и infrastructure owners; работа связана с A07 и A14.

## 10. P2 — командная работа и релизная дисциплина

### TEAM-01. Ввести краткий асинхронный статус

Результат: состояние задач и blockers доступно без регулярного ручного опроса.

Критерии приёмки:
- Участники сообщают завершённое, следующую работу и blockers в согласованном канале.
- Blocker содержит ожидаемое и фактическое поведение, диагностику, уже выполненные действия и необходимую помощь.
- У blocker назначены ответственный и следующее действие.
- Team Lead разрешает приоритеты и зависимости; реализация остаётся у владельца задачи.

### ADR-01. Документировать существенные архитектурные решения

Результат: для решений с долгосрочными последствиями доступна причина выбора.

Критерии приёмки:
- ADR содержит Context, Decision, Alternatives и Consequences.
- Указаны авторы, дата и статус решения.
- Документируется принятое решение; не создаются записи, выдающие исторические предположения за факты.
- Изменение API-контракта, хранения данных или модели deployment согласуется участвующими владельцами.

### REL-01. Подготовить регламент демонстрации и релиза

Результат: релиз воспроизводим и не зависит от срочных изменений перед демонстрацией.

Критерии приёмки:
- Определены feature freeze, release candidate и список известных дефектов.
- Выполнены critical regression, backup и проверка rollback readiness.
- После deployment пройден smoke.
- Назначены ответственный за релиз и резервный участник.
- Новые migrations и крупные features после freeze требуют явного решения.
- CI-green не подменяет выполнение release checklist.

## 11. P3 — последующие улучшения

После выполнения обязательных задач отдельно оценить:
- Dependabot или Renovate с ограничением количества одновременных PR.
- Расширение SAST, container, secret и dependency scanning открытыми инструментами.
- Coverage reports в локальном окружении или Actions artifacts.
- Performance/load tests на стенде с согласованными лимитами.
- Preview-окружения на существующих ресурсах при наличии бюджета.
- Дополнительные E2E, changelog/releases и deployment notifications.

Для каждой инициативы требуется конкретная проблема, ожидаемая польза, стоимость поддержки и критерий завершения. Платные GitHub-функции и внешние подписки не входят в этот этап.

## 12. Очерёдность и показатели результата

Начальная последовательность:
1. TL-01–TL-03 и PM-01: ответственность, review и понятные задачи.
2. CI-01: ошибки CI и зависимости publish/deploy; A01 до следующего infrastructure deployment.
3. Приоритетные исправления A02/A03/A04/A05 и A16 с проверкой текущего статуса Issues.
4. QA-01–QA-03 и DOC-01: доказательства качества и передача знаний.
5. OBS-01, REC-01, DATA-01 и остальные эксплуатационные задачи.

Метрики снимаются регулярно после определения исходных значений:
- доля обычных PR, требующих участия Team Lead;
- время ожидания review и число PR без назначенного reviewer;
- повторные вопросы, для которых отсутствует пригодная документация;
- число штатных deployment/maintenance операций с ручным вмешательством;
- длительность самостоятельной работы команды при отсутствии Team Lead;
- доля задач, завершённых с доказательством критериев приёмки.

Конкретные целевые значения согласуются после первого периода измерений. Новые подсистемы не добавляются только ради выполнения формального checklist.
